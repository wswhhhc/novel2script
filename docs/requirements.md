# AI 小说转剧本工具需求文档

## 1. 项目概述

### 1.1 项目名称

Novel2Script：AI 小说转剧本创作助手

### 1.2 项目背景

很多小说作者希望将自己的作品改编为短剧、影视剧本、广播剧或分镜脚本，但小说和剧本在表达方式上存在明显差异。小说通常依赖叙述、心理描写、环境描写和作者语言风格，而剧本更强调场景、人物动作、对白、冲突推进和可拍摄性。

传统改编过程需要作者具备一定剧本创作经验，门槛较高、耗时较长。本项目希望借助 AI 的文本理解和生成能力，帮助作者快速完成从小说章节到结构化剧本初稿的转换。

### 1.3 项目目标

本项目旨在开发一款 AI 辅助剧本创作工具，支持用户输入 3 个章节以上的小说文本，自动生成符合 YAML Schema 的结构化剧本初稿，让作者能够快速获得可编辑、可校验、可继续打磨的剧本内容。

项目核心目标包括：

- 降低小说改编为剧本的门槛。
- 提升剧本初稿生成效率。
- 生成结构化 YAML 剧本，便于后续编辑、校验和导出。
- 保留小说章节与剧本场景之间的对应关系。
- 提供 YAML Schema 文档，说明结构设计和设计原因。

## 2. 用户与使用场景

### 2.1 目标用户

- 小说作者：希望将原创小说改编成剧本初稿。
- 编剧初学者：希望借助 AI 理解小说改编流程。
- 短剧创作者：希望快速获得分场剧本和对白初稿。
- 内容团队：希望批量处理小说章节，辅助 IP 改编评估。

### 2.2 典型使用场景

用户拥有一篇不少于 3 个章节的小说文本，希望快速生成剧本初稿。用户将小说粘贴到系统或上传文本文件，点击生成后，系统自动识别章节、分析人物和剧情，并输出 YAML 格式剧本。用户可以查看、修改、下载结果，也可以基于 YAML 内容继续进行二次创作。

## 3. 产品范围

### 3.1 MVP 范围

第一阶段只实现最小可用版本，重点验证核心链路：

1. 用户输入或上传小说文本。
2. 系统自动识别章节。
3. 系统判断章节数量是否不少于 3 个。
4. 系统调用 AI 生成结构化剧本。
5. 系统按照 YAML Schema 校验生成结果。
6. 前端展示 YAML 剧本内容。
7. 用户可以下载 YAML 文件。

### 3.2 暂不实现内容

以下功能不纳入 MVP，可作为后续扩展：

- 用户登录和权限管理。
- 多人协作编辑。
- 分镜图片生成。
- 视频生成。
- 完整剧本文档排版系统。
- 商业版权检测。

### 3.3 MVP 扩展功能（Phase 6）

第六阶段在不引入登录、云同步和多人协作的前提下，补充轻量创作工作台能力：

- 本地项目保存和管理。
- YAML 版本快照和恢复。
- 多格式导出：YAML / JSON / Markdown。
- SQLite 本地存储，所有项目仅在当前服务实例内共享。

## 4. 功能需求

### 4.1 小说文本导入

#### 功能说明

用户可以通过文本框粘贴小说内容，也可以上传 `.txt` 或 `.md` 格式文件。

#### 输入要求

- 文本内容必须包含 3 个章节以上。
- 单次输入文本长度上限：50,000 字（约 75k tokens）。
- 单个章节建议长度：3,000-8,000 字。
- 支持最大章节数：20 个章节。
- 支持常见章节标题格式，例如：
  - 第1章 / 第一章
  - Chapter 1 / Chapter One
  - 1. / 一、
  - 卷一 第一章
  - 纯标题格式（由 AI 智能识别）

#### 输出结果

系统返回识别出的章节列表，包括章节编号、章节标题和章节正文。

### 4.2 章节识别与校验

#### 功能说明

系统自动识别小说章节，并判断是否满足题目要求的 3 个章节以上。

#### 章节识别策略

采用多层次识别策略，优先级从高到低：

1. **正则表达式匹配**：识别常见章节格式
   - `第[0-9一二三四五六七八九十百千]+章`
   - `Chapter\s+[0-9]+`
   - `^[0-9]+[\.\、]`
   - `^[一二三四五六七八九十]+[\.\、]`
   
2. **AI 智能识别**：当正则匹配失败时
   - 分析文本结构特征
   - 识别重复出现的标题模式
   - 推断章节边界
   
3. **用户手动标注**：当自动识别失败时
   - 提供交互式标注界面
   - 用户可手动标记章节分隔位置

#### 校验规则

- 若章节数量小于 3，系统提示："章节数量不足，需要至少 3 个章节，当前识别到 X 个章节"。
- 若无法识别章节，系统提示："无法自动识别章节格式，请检查章节标题格式或使用手动标注"。
- 若章节正文为空，系统提示："第 X 章内容为空，请检查输入内容"。
- 若单个章节超过 10,000 字，系统提示："第 X 章内容过长（X 字），建议拆分或可能影响生成质量"。

### 4.3 小说内容分析

#### 功能说明

系统调用 AI 对小说内容进行分析，提取剧本改编所需的信息。

#### 分析内容

- 每章摘要
- 主要人物
- 人物身份
- 人物关系
- 关键事件
- 场景地点
- 时间线索
- 冲突与悬念
- 可改编为对白的内容

### 4.4 角色表生成

#### 功能说明

系统根据小说内容生成角色表，为后续剧本中的人物引用提供统一依据。

#### 角色字段

- 角色 ID
- 角色姓名
- 角色定位
- 人物简介
- 性格特征
- 首次出场章节
- 与其他角色的关系

### 4.5 场景拆分

#### 功能说明

系统根据小说剧情，将章节内容拆分为多个剧本场景。

#### 场景字段

- 场景 ID
- 场景标题
- 来源章节
- 场景地点
- 场景时间
- 出场角色
- 场景目的
- 场景内容

### 4.6 剧本内容生成

#### 功能说明

系统将小说内容改写为剧本格式，重点生成动作、对白、旁白和转场等结构化内容。

#### 内容类型

- action：人物动作或场景动作
- dialogue：人物对白
- narration：旁白或画外音
- transition：转场提示
- note：创作备注

#### 生成要求

- 对白应符合人物身份和情绪。
- 动作描写应具备可视化和可拍摄性。
- 心理描写应尽量转化为动作、对白或旁白。
- 长篇叙述应适度压缩，避免直接照搬小说原文。
- 场景之间应保持剧情连续性。

### 4.7 YAML 剧本输出

#### 功能说明

系统按照预设 YAML Schema 输出结构化剧本。

#### 输出内容

- 剧本基本信息
- 小说来源章节
- 角色表
- 场景列表
- 场景内剧本内容
- 改编说明
- 待确认问题

### 4.8 YAML Schema 校验

#### 功能说明

系统需要校验 AI 输出是否符合预定义 YAML Schema。

#### 校验内容

- 必填字段是否存在。
- 字段类型是否正确。
- 场景 ID 是否唯一。
- 角色引用是否能在角色表中找到。
- 来源章节是否能在章节列表中找到。
- `beats` 中的 `type` 是否为允许值。

#### 异常处理

如果校验失败，系统应返回错误信息，并可尝试让 AI 根据错误信息自动修复 YAML。

### 4.9 YAML 预览与编辑

#### 功能说明

前端提供 YAML 编辑器，用户可以查看和修改生成结果。

#### 编辑要求

- 支持代码高亮。
- 支持基本格式检查。
- 支持复制 YAML 内容。
- 支持下载 YAML 文件。

### 4.10 结果导出

#### MVP 导出

- `.yaml` 文件导出。

#### Phase 6 扩展导出

- `.json` 文件导出。
- `.md` 分场大纲导出。

#### 后续扩展导出

- `.docx` 剧本文档导出。

## 5. 非功能需求

### 5.1 性能指标

- 章节识别响应时间：< 5 秒
- 剧本生成时间：
  - 3-5 章节：< 60 秒
  - 6-10 章节：< 120 秒
  - 11-20 章节：< 180 秒
- YAML 校验时间：< 2 秒
- 前端页面加载时间：< 3 秒
- 文件上传支持：最大 10MB

### 5.2 易用性

- 用户无需了解专业剧本格式即可使用。
- 输入、生成、编辑、下载流程应清晰。
- 错误提示应具体，例如：
  - "章节数量不足，需要至少 3 个章节，当前识别到 2 个章节"
  - "第 3 章内容为空，请检查输入"
  - "生成失败：AI 服务超时，请稍后重试"
  - "YAML 校验失败：场景 S005 引用了不存在的角色 C999"

### 5.3 稳定性

- AI 输出结果必须经过 Schema 校验。
- 后端需要处理模型调用失败、超时、返回空内容等异常情况。
- 对超长文本应提供提示或分段处理策略：
  - 单章节超过 10,000 字时提示警告
  - 总字数超过 50,000 字时拒绝处理
- AI 调用超时设置：120 秒
- 自动重试机制：失败后最多重试 2 次，间隔 3 秒

### 5.4 可扩展性

- YAML Schema 应支持后续扩展字段。
- AI 模型调用层应支持切换不同模型供应商（OpenAI、Anthropic、Azure OpenAI）。
- 剧本内容类型应支持新增，例如 shot、music、sound_effect 等。
- 支持插件化扩展新的导出格式。

### 5.5 可维护性

- 前后端分离。
- Prompt 模板独立维护（存放在 `prompts/` 目录）。
- Schema 定义和校验逻辑独立维护（存放在 `schemas/` 目录）。
- 示例输入和示例输出放入 `examples/` 目录。
- 配置文件集中管理（`config/` 目录）。
- 代码注释覆盖率 > 60%。
- 关键函数需要单元测试。

## 6. 系统流程

### 6.1 主流程

```text
用户输入小说文本
-> 系统识别章节
-> 校验章节数量
-> AI 分析章节内容
-> AI 生成角色表和场景大纲
-> AI 按 YAML Schema 生成剧本
-> 系统校验 YAML
-> 前端展示生成结果
-> 用户编辑或下载 YAML
```

### 6.2 AI 生成流程

为了提高生成稳定性，AI 不应直接一次性从小说生成最终剧本，而是采用分阶段生成：

1. 章节分析阶段：提取摘要、事件、人物和地点。
2. 结构规划阶段：生成角色表和场景列表。
3. 剧本生成阶段：根据 Schema 生成完整 YAML。
4. 校验修复阶段：若 YAML 不合法，则根据错误信息自动修复。

## 7. 页面需求

### 7.1 首页 / 工作台

页面主要区域：

- 小说输入区
- 文件上传按钮
- 章节识别结果
- 生成剧本按钮
- YAML 输出区
- 下载按钮

### 7.2 推荐布局

```text
左侧：小说输入和章节列表
中间：生成设置和分析结果
右侧：YAML 编辑器和下载操作
```

### 7.3 页面状态

页面需要支持以下状态：

- **初始状态**：等待用户输入
- **文本已输入**：显示字数统计和"识别章节"按钮
- **章节识别中**：显示加载动画，预计 2-5 秒
- **章节识别成功**：展示章节列表，每个章节显示编号、标题、字数
- **章节数量不足**：高亮提示并禁用"生成剧本"按钮
- **AI 生成中**：显示进度条和当前阶段
  - 分析章节内容（30%）
  - 生成角色表和场景（60%）
  - 生成完整剧本（90%）
  - 校验和修复（100%）
- **生成成功**：展示 YAML 编辑器和下载按钮
- **Schema 校验失败**：显示具体错误信息和修复建议
- **下载完成**：显示成功提示

### 7.4 交互流程细节

#### 用户上传小说后

1. 显示"正在识别章节..."加载状态（预计 2-5 秒）
2. 识别成功后展示章节列表，每个章节显示：
   - 章节编号（如 C001）
   - 章节标题
   - 字数统计
   - 可折叠查看正文
3. 章节不足 3 个时：
   - 红色高亮提示："需要至少 3 个章节，当前只有 X 个"
   - 禁用"生成剧本"按钮
4. 生成过程显示进度和预计时间：
   - 进度条显示当前百分比
   - 文字提示当前阶段
   - 显示预计剩余时间

#### 生成完成后

1. YAML 编辑器自动加载内容
2. 支持语法高亮和折叠
3. 显示校验结果（通过/失败）
4. 提供操作按钮：
   - 复制 YAML
   - 下载 YAML 文件
   - 重新生成
   - 编辑后重新校验

## 8. 接口需求

### 8.1 章节解析接口

```text
POST /api/chapters/parse
```

请求：

```json
{
  "content": "小说全文"
}
```

响应：

```json
{
  "chapter_count": 3,
  "chapters": [
    {
      "id": "C001",
      "title": "第一章 雨夜来客",
      "content": "章节正文"
    }
  ]
}
```

### 8.2 剧本生成接口

```text
POST /api/script/generate
```

请求：

```json
{
  "title": "小说标题",
  "genre": "悬疑",
  "chapters": []
}
```

响应：

```json
{
  "yaml": "script:\n  title: ...",
  "validation": {
    "valid": true,
    "errors": []
  }
}
```

### 8.3 YAML 校验接口

```text
POST /api/script/validate
```

请求：

```json
{
  "yaml": "script:\n  title: ..."
}
```

响应：

```json
{
  "valid": true,
  "errors": []
}
```

## 9. YAML 输出要求

生成的 YAML 剧本应包含以下顶层结构：

```yaml
script:
  title: string
  genre: string
  version: string
  source:
    chapter_count: number
    chapters: []
  characters: []
  scenes: []
  adaptation_notes: []
  open_questions: []
```

### 9.1 字段约束规则

#### script 顶层字段

```yaml
script:
  title: string          # 必填，剧本标题，1-100 字符
  genre: string          # 必填，类型（如：都市、悬疑、古装、科幻）
  version: string        # 必填，版本号（如：1.0.0）
  created_at: string     # 可选，生成时间（ISO 8601 格式）
```

#### source 字段

```yaml
source:
  chapter_count: number  # 必填，源章节数量
  chapters:              # 必填，章节列表
    - id: string         # 必填，格式：C001-C999，唯一
      title: string      # 必填，章节标题
      word_count: number # 可选，章节字数
```

#### characters 字段

```yaml
characters:
  - id: string                    # 必填，格式：CHAR001-CHAR999，唯一
    name: string                  # 必填，角色姓名，2-20 字符
    role: string                  # 必填，如：主角、配角、群众
    description: string           # 可选，人物简介，最多 500 字符
    personality: string[]         # 可选，性格特征列表
    first_appearance: string      # 必填，首次出场章节，引用 chapter.id
    relationships:                # 可选，人物关系
      - character_id: string      # 关系对象，引用其他 character.id
        relation: string          # 关系描述（如：朋友、敌人、恋人）
```

#### scenes 字段

```yaml
scenes:
  - id: string                    # 必填，格式：S001-S999，唯一
    title: string                 # 必填，场景标题
    source_chapters: string[]     # 必填，来源章节列表，引用 chapter.id
    location: string              # 必填，场景地点
    time: string                  # 必填，场景时间（如：白天、夜晚、黄昏）
    characters: string[]          # 必填，出场角色列表，引用 character.id
    purpose: string               # 必填，场景目的，说明该场景的剧情作用
    beats: []                     # 必填，场景内容，至少 3 个 beats
```

#### beats 字段

```yaml
beats:
  - type: string                  # 必填，类型：action | dialogue | narration | transition | note
    text: string                  # 必填，内容文本
    character: string             # 当 type=dialogue 时必填，引用 character.id
    emotion: string               # 当 type=dialogue 时可选，情绪描述
    notes: string                 # 可选，创作备注
```

**beats 类型说明：**
- `action`：人物动作或场景动作描写
- `dialogue`：人物对白（必须包含 character 和 text）
- `narration`：旁白或画外音
- `transition`：转场提示（如：淡入、切至、叠化）
- `note`：创作备注或待确认问题

#### adaptation_notes 字段

```yaml
adaptation_notes:
  - type: string                  # 必填，类型：deletion | merge | transformation | addition
    description: string           # 必填，说明改编的具体内容
    reason: string                # 必填，改编原因
```

#### open_questions 字段

```yaml
open_questions:
  - question: string              # 必填，待确认的问题
    context: string               # 可选，问题相关的上下文
```

每个场景应包含：

```yaml
- id: S001
  title: string
  source_chapters: []
  location: string
  time: string
  characters: []
  purpose: string
  beats: []
```

每个 beat 应包含：

```yaml
- type: action | dialogue | narration | transition | note
  text: string
```

当 `type` 为 `dialogue` 时，还应包含：

```yaml
character: string
emotion: string
```

完整 Schema 设计原因应在 `docs/yaml-schema.md` 中单独说明。

### 10.3 AI 模型接入

系统应将模型调用封装为独立服务，支持通过配置切换不同模型供应商。

推荐环境变量：


### 10.4 AI Prompt 设计策略

#### 设计原则

1. **使用 Few-shot 示例**：每个阶段提供 1-2 个完整示例，稳定输出格式
2. **明确输出格式约束**：提供 JSON Schema 或完整 YAML 示例
3. **分段处理策略**：
   - 单章节超过 8,000 字时先生成摘要
   - 基于摘要生成场景大纲
   - 再基于大纲和原文生成详细剧本
4. **使用思维链（Chain of Thought）**：引导 AI 逐步推理
5. **角色一致性约束**：明确要求所有角色必须先在角色表中定义

#### Prompt 模板结构

所有 Prompt 模板应存放在 `prompts/` 目录，包括：

- `prompts/01_chapter_analysis.txt`：章节分析阶段
- `prompts/02_character_extraction.txt`：角色提取阶段
- `prompts/03_scene_planning.txt`：场景规划阶段
- `prompts/04_script_generation.txt`：剧本生成阶段
- `prompts/05_yaml_fix.txt`：YAML 修复阶段

每个 Prompt 应包含：
- 任务说明
- 输入格式
- 输出格式（带示例）
- 注意事项
- Few-shot 示例

#### 生成流程

```text
输入小说章节
  ↓
阶段 1: 章节分析（提取摘要、人物、事件、地点）
  ↓
阶段 2: 角色表生成（统一角色信息）
  ↓
阶段 3: 场景规划（拆分场景、分配角色）
  ↓
阶段 4: 剧本生成（按 YAML Schema 生成完整剧本）
  ↓
阶段 5: 校验与修复（若不合法则自动修复，最多 3 次）
  ↓
输出最终 YAML
```

## 11. 验收标准

### 11.1 功能验收

- 能输入或上传小说文本。
- 能识别出 3 个以上章节。
- 当章节不足 3 个时，系统能给出明确提示。
- 能调用 AI 生成 YAML 格式剧本。
- 生成结果符合预定义 YAML Schema。
- 能展示 YAML 内容。
- 能下载 YAML 文件。
- 项目包含 YAML Schema 设计文档。

### 11.2 内容验收

- 角色表信息基本完整。
- 场景划分与原小说剧情相关。
- 对白和动作能够体现剧本形式。
- 每个场景能追溯到来源章节。
- 改编说明能解释主要删减、合并或转换逻辑。

### 11.3 质量标准

#### 最低质量要求

- **角色名称一致性**：同一角色在所有场景中名称必须统一（100% 一致）
- **场景完整性**：每个场景必须包含至少 3 个 beats
- **对白合理性**：对白数量占比应在 40%-70% 之间
- **来源可追溯**：每个场景必须能追溯到源章节
- **时间线连贯**：场景时间不能出现明显矛盾
- **角色引用合法性**：所有场景中引用的角色必须在角色表中存在
- **ID 唯一性**：所有 ID（章节、角色、场景）必须唯一

#### 可选质量指标（用于后续优化）

- 角色出场频率与原小说相符度 > 80%
- 关键剧情保留完整度 > 90%
- 场景拆分合理性（人工评估，每个场景聚焦单一事件）
- 对白符合人物性格（人工评估）
- 动作描写具备可拍摄性（人工评估）

### 11.4 工程验收

- 前后端目录结构清晰。
- 接口命名清楚。
- Prompt、Schema、业务逻辑分离。
- 有示例小说输入和示例 YAML 输出。
- 有 README 或运行说明。
- 代码有适当注释。
- 关键函数有单元测试。

## 13. 项目风险与应对

### 13.1 AI 输出格式不稳定

应对方式：

- 使用明确的 YAML Schema。
- 在 Prompt 中提供完整示例。
- 后端增加 Schema 校验。
- 校验失败时触发自动修复。

### 13.2 输入文本过长

应对方式：

- 限制单次输入长度。
- 按章节分批分析。
- 先生成章节摘要，再基于摘要生成剧本。

### 13.3 改编质量不稳定

应对方式：

- 将生成流程拆成分析、规划、生成三个阶段。
- 保留来源章节映射。
- 输出改编说明，方便人工判断。

### 13.4 人物名称不一致

应对方式：

- 先生成统一角色表。
- 后续场景中的人物只能引用角色表中的角色。
- 校验角色引用是否合法。
